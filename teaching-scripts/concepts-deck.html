01 · Foundations React vs Next.js

React is the engine.
Next.js is the car.

React is a UI library — it renders components and stops there. Next.js is the full-stack framework around it: routing, data loading, server rendering, API endpoints. The big move: it does the work on the server, before the browser sees a byte.

Say it like this: with CSR the browser gets an empty div and a to-do list. With SSR the server already did the to-do list — the first byte of HTML has your data in it.

02 · Foundations How SSR actually works

The server renders.
The browser hydrates.

Server Components run as Node.js functions — they can await databases, secrets, files. They emit finished HTML and ship zero component JavaScript. Hydration then attaches event listeners to the HTML that's already on screen — no repaint, no re-fetch.

Only Client Components hydrate. Server Components never run in the browser — their JS never even downloads.

Misconception to kill early: SSR ≠ "rendered once at build time". On our defaults, every request re-runs the Server Components — data is always fresh.

04 · Session 1 — Routing The folder structure IS the router

There is no router config.
The file's path is its URL.

Every router you've ever used was a mapping from URL patterns to components, kept in a config file. Next.js makes the mapping structural — the file system already has paths, so it becomes the route tree. See a folder, see a URL.

src/app/page.tsx

src/app/(s1-routing)/about/page.tsx
/about
↑ (parentheses) = route group — organizes files, invisible in the URL
src/app/(s1-routing)/blog/page.tsx
/blog
src/app/(s1-routing)/blog/[slug]/page.tsx
/blog/:anything
↑ [brackets] = dynamic segment — captures the URL part as a param
src/app/(s1-routing)/layout-demo/settings/page.tsx
/layout-demo/settings

The quiz that proves it: "Where would a file go to make /about/team?" → about/team/page.tsx. If you can create a file in the right place, you've created a route.

06 · Session 1 — Routing The v16 headline

params is a Promise now.
You await it.

The single biggest v16 breaking change. params and searchParams are Promises — in the page and in generateMetadata. Every old tutorial doing params.slug directly will error in v16.

src/app/(s1-routing)/blog/[slug]/page.tsxexport default async function BlogPostPage({ params }: {
  params: Promise<{ slug: string }>;   // ← a Promise, not an object
}) {
  const { slug } = await params;       // ← THE v16 habit to build
  const post = await getPostBySlug(slug);
  if (!post) notFound();
  return <article>…</article>;
}

export async function generateMetadata({ params }) {
  const { slug } = await params;       // ← same rule here — per-page <title>
  return { title: (await getPostBySlug(slug))?.title };
}

Why the change? Awaiting these lets Next start rendering the rest of the page before the values resolve — it's what makes streaming possible. Same rule for cookies(), headers(), draftMode() — all async-only in v16.

08 · Session 1 — Routing Layouts nest

Layouts stay mounted.
Only {children} swaps.

A layout.tsx wraps every page in its folder and all child folders — pages never import it; they inherit it by position in the tree. On navigation, parent layouts (and their state, and your scroll position) stay mounted. That's why there's no flicker.

Watch the dashed region — navigating Overview ↔ Settings swaps only that {children} slot. Both layouts never re-mount.

Quiz: "Where do <html> and <body> come from?" → the root layout.tsx — the only place they live.

09 · Session 2 — Components The single most important idea

Server by default.
'use client' is the opt-in.

Components render on the server unless you say otherwise. Reach for 'use client' only for interactivity — state, effects, event handlers, browser APIs — and keep it small. Client components are the exception, not the rule.

Server Component

the default — no directive needed
  • ✓
    async + await data inlinereads DB, secrets, files — safely
  • ✓
    Ships 0 KB of component JSthe browser gets finished HTML
  • ✗
    No useState / useEffect / onClickno lifecycle, no DOM — it never re-renders
  • ✗
    No window / localStoragethere is no browser here

Client Component

'use client' — first line of the file
  • ✓
    Hooks, events, browser APIsthis is the whole point
  • ✓
    Hydrates and stays interactivestate survives across renders
  • ✗
    Can't import server data functionsmust fetch over HTTP via a Route Handler
  • ✗
    Its code ships in the bundleand so does everything it imports…

The one deciding question: does this component need state, effects, events, or browser APIs? No → server (default). Yes → a small 'use client' leaf.

10 · Session 2 — Components 'use client' is a boundary, not a switch

Draw the line
as low as you can.

Once a file is marked 'use client', everything it imports becomes client too. Mark the top of the tree and you've dragged the whole page into the browser. Mark only the interactive leaf, and everything above it stays on the server.

✗ 'use client' at the top

page.tsx 'use client'
<Heading/>
<UserList/>
<Counter/>
the whole tree ships to the browser — JS, hydration, spinners

✓ 'use client' at the leaf

page.tsx — server, async, awaits data
<Heading/>
<UserList/>
<Counter/> leaf
only the button's useState + onClick ships — the rest is HTML

Composition rule: a Server Component can render a Client Component freely (server page → client leaf). A Client Component can't import a Server Component — but it can receive one as children (the "slot" pattern).

12 · Session 2 — Components Rendering, Suspense & streaming

Slow data?
Stream the skeleton first.

A slow await shouldn't mean a blank screen. Drop a loading.tsx in the route folder — Next auto-wraps the page in a <Suspense> boundary. You wrote zero loading-state code. loading.tsx is Suspense, with a default boundary.

Browser
Next.js server
GET /dashboard
loading.tsx skeleton — streamed instantly
await getSlowSummary() — 2s
behind the skeleton, not in front of the user
real content streams in, swaps the skeleton
The user sees structure immediately, never a blank screen. Perceived speed beats actual speed.

Finer control: loading.tsx streams the whole route as one unit. For per-section streaming, wrap individual async components in their own <Suspense fallback> — a fast card never waits for a slow one (/dashboard/granular).

13 · Session 2 — Components Don't build waterfalls

Independent fetches?
Start them together.

await one thing, then await the next, and you've built a waterfall — each request waits for the last. For independent data, Promise.all starts them in parallel.

14 · Session 3 — Actions The write half of the loop

Write data with
one function, zero client code.

HTML forms have posted to servers since 1993 — no JS required. Server Actions restore that: a real <form> posts straight to a 'use server' function. It mutates, calls revalidatePath, and the list refreshes. No onSubmit, no fetch, no manual re-fetch.

<form action={fn}>
real form, server-rendered — works with JS off
native POST
'use server' fn
runs ONLY on the server · gets FormData
validate + mutate
DB / store — user can't bypass it
revalidatePath('/guestbook')
"this route's data changed"
page re-renders
fresh HTML streams back — new entry on top
One round trip does both the mutation and the UI update. There is no client state in this picture at all.
guestbook/actions.ts · guestbook/page.tsx'use server';                                  // every export = a Server Action
export async function signGuestbook(formData: FormData) {
  const name = String(formData.get('name') ?? '');
  if (!name) return;                           // validation runs on the server
  await addGuestbookEntry(name);
  revalidatePath('/guestbook');                // re-render the list — no manual re-fetch
}

// page.tsx — a Server Component. Pass the function straight to the form:
<form action={signGuestbook}> … </form>

Two call-outs: ① turn JS off in devtools and submit — it still works (progressive enhancement). ② Actions are reachable by direct POST, not just your form — real apps must check auth inside every action.

15 · Session 3 — Actions Pending & error UI

Need feedback?
That's useActionState's one job.

The plain form is submit-and-hope. When a form needs a pending flag or validation errors, opt in: a small client leaf with useActionState. The action's signature changes — it takes (previousState, formData) and returns the next state.

does this form need a pending flag or error UI?
no — most forms
plain <form action={fn}>
stays a Server Component — guestbook, todo-toggle rows
yes — live feedback
'use client' leaf + useActionState
the add-todo form: "Adding…", red error text

todos/add-todo-form.tsx (client leaf) · todos/actions.ts (server)'use client';
const [state, formAction, pending] = useActionState(addTodoAction, {});
// <form action={formAction}> · <button disabled={pending}> · {state.error && <p>…</p>}

'use server';
export async function addTodoAction(prevState, formData) {
  const text = String(formData.get('text') ?? '');
  if (!text) return { error: 'Todo cannot be empty' };  // ← returned state
  await addTodo(text);
  revalidatePath('/todos');
  return {};
}

Same leaf principle as the counter: only the add-form is a client component. The page, the list, and every toggle-row form stay server-rendered.

17 · v16 & beyond Why old tutorials are wrong

What changed
in Next.js 16.

Most online tutorials and Stack Overflow answers were written for v13/14/15 — these are the deltas that make them subtly wrong.

await params · cookies() · headers()

All dynamic APIs are Promises now. The sync form warned in v15; in v16 it's removed. params.slug without await = error.

Turbopack is the default

For both dev and build — no --turbopack flag. Fall back with next dev --webpack if ever needed.

middleware.ts → proxy.ts

Renamed to clarify it's a network-boundary proxy. Runs on the Node.js runtime — edge isn't supported in proxy.

Node ≥ 20.9 · React 19.2

Older Node won't run v16. React 19.2 is built into the App Router — useActionState comes from it.

next lint is gone

The next lint command was removed — bring your own tooling. This course uses Biome: pnpm lint.

revalidateTag(tag, profile)

Got a 2-arg signature; the 1-arg form is deprecated. But revalidatePath('/x') — what we use — is unchanged.

18 · v16 & beyond proxy.ts — the front door

One function runs
before every route.

v16 renamed middleware.ts → proxy.ts to say what it really is: a proxy at the network boundary, in front of your whole app. One file at the project root — every matched request passes through it before any page, Route Handler, or Server Action runs.

any request from the browser
GET /todos · GET /api/users · form POST (a Server Action)
proxy.ts — one function, runs first
redirect · rewrite · or pass through
it's a page
page.tsx renders
Server Components run
it's an API route
route.ts GET/POST
Route Handler runs
it's a form submit
'use server' action
a POST to its own route — goes through the proxy too
The decision happens before any route code runs — redirect it, rewrite it, or let it through. Server Actions are just POSTs, so they pass through it too.
proxy.ts — project root, next to src/import { NextResponse, type NextRequest } from 'next/server';

export function proxy(request: NextRequest) {
  const session = request.cookies.get('session');     // read the request — no DB call
  if (!session) {
    return NextResponse.redirect(new URL('/login', request.url));
  }
  return NextResponse.next();                        // fall through to the route
}

export const config = {
  matcher: ['/todos/:path*', '/guestbook/:path*'],  // only these URLs pass through
};

v16 notes: the function is named proxy, it runs on the Node.js runtime (edge isn't supported here), and middleware.ts is deprecated — npx @next/codemod middleware-to-proxy renames an old project for you. Without a matcher it runs on every request — even prefetches and static assets.

19 · v16 & beyond What the proxy is for

Cross-cutting checks.
Not business logic.

The proxy is for decisions you can make from the request alone — a cookie, a header, the URL — applied to many routes at once. The classic example is the auth gate:

✓ has a session cookie — pass through NextResponse.next()

✗ no cookie — turned away at the door NextResponse.redirect()

/login renders
todos code never ran
auth gate

Read the session cookie, redirect to /login — an optimistic check for whole sections of the app.

redirects

Programmatic redirects from request properties — old URLs, locales, logged-in users straight to /dashboard.

rewrites / A·B tests

NextResponse.rewrite() serves variant B under the same URL — the address bar never changes.

headers & CORS

Stamp security or CORS headers on every response from one place instead of every route.

bots & geo

Block by User-Agent, route by country — decisions made purely from request metadata.

logging

One choke point sees every request — request-level logging and metrics live naturally here.

✗ keep OUT of the proxy — it runs on every matched request, even prefetches

DB queries / slow fetches
latency added to every single request
your only auth check
actions are reachable by direct POST — re-verify inside each one
business logic
belongs in pages, actions, Route Handlers

The deciding question: can you make this call from the request alone — cookie, header, URL? Yes → proxy. Needs your data or your DB? It belongs in the route. The proxy is a bouncer, not the kitchen.
