1React vs Next.js — and what is Server-Side Rendering?

React is a UI library. Next.js is a full-stack framework built on React. The key difference: React renders in the browser; Next.js moves most of that work to the server before the browser ever sees a byte.
Philosophy React answered "how do we build UIs?" — and stopped there by design. Next.js answers the follow-up: "but where should those UIs run, how do they get data, and how do we route between them?" These are framework concerns, not library concerns. Next.js uses React as its rendering engine and adds everything around it.

React alone: the browser does everything (CSR)

A plain React app (Vite, Create React App) ships the browser a near-empty HTML file plus a large JavaScript bundle. The browser downloads the JS, parses it, runs it, and then your page appears. During that gap the user sees a blank screen. This is Client-Side Rendering (CSR).

sequenceDiagram
  participant B as Browser
  participant S as Static Server
  B->>S: GET /dashboard
  S-->>B: <html><div id="root"></div> + big bundle.js
  Note over B: blank screen while JS downloads & parses
  B->>B: React renders components
  B->>B: useEffect fires → fetch /api/data
  Note over B: spinner → data arrives → page visible ✓

With CSR the HTML that arrives is empty. Crawlers and users see nothing until JavaScript has run — and data hasn't even loaded yet.

Next.js: the server does the work first (SSR)

Server-Side Rendering means the server runs your components, fetches the data, and generates complete HTML — before it responds. The browser receives a fully-populated page on the very first byte. No spinner. No blank screen. Content is visible before a single line of your JavaScript executes.

sequenceDiagram
  participant B as Browser
  participant N as Next.js (Node.js server)
  B->>N: GET /dashboard
  N->>N: run Server Components,
await DB / fetch
  N-->>B: <html>...full rendered content...</html>
+ thin hydration JS
  Note over B: page visible immediately ✓
  B->>B: hydrate — attach event listeners
(no repaint, no re-fetch)

With SSR the HTML is fully populated on arrival. Hydration adds interactivity without repainting anything the user already sees.

How Next.js achieves SSR — the mechanism

The mechanism in the App Router is Server Components. Next.js runs these in Node.js during the request. They can await databases, secrets, files — anything server-side. They emit HTML and send zero component JavaScript to the browser. Client Components ('use client') are the thin interactive layer that hydrates in the browser afterward.

A common misconception

"SSR" in Next.js doesn't mean the server generates HTML once and caches it forever (that's Static Site Generation, SSG). By default, App Router pages render fresh on every request — the server runs your Server Components each time, so the data is always current. Caching is a separate opt-in (day-2 topic).

3App Router: the folder structure is the router

There is no router config file. A file's path under src/app/ is its URL. Special filenames add behavior with zero wiring.

Philosophy — Convention over Configuration Every router you've ever configured has been a mapping from URL patterns to components. Next.js makes that mapping structural — the file system already has a hierarchical path representation, so it becomes the route tree. No config to sync, no typos to introduce, no indirection to follow. When you see a folder, you see a URL. This is Rails-style convention applied to React.

The special files (own this table)

Two folder-name conventions

  • (group) — route group. Organizes files; invisible in the URL. (s1-routing)/about/page.tsx → /about.
  • [slug] — dynamic segment. Captures the URL part as a param. blog/[slug]/page.tsx → /blog/anything.

Layouts nest; only {children} swaps

Navigating between sibling pages re-renders only the inner {children} region. Parent layouts (and their state, scroll position, the sidebar) stay mounted — that's why there's no flicker. The root layout.tsx is the only place <html> / <body> live.

v16 headline you must drill

params and searchParams are Promises — you must await them, in both the page and generateMetadata. Any tutorial doing params.slug directly is pre-v15-style and will error in v16.

4Server vs Client Components — the single most important idea

Components render on the server by default. 'use client' opts a file (and everything it imports) into the browser bundle. Reach for it only for interactivity — state, effects, event handlers, browser APIs — and keep it at the leaves.
Philosophy — Server first, client at the edge The web's original model was server-rendered HTML. Single-page apps flipped that: move everything to the client. React Server Components flip it back, but smarter: keep data access and static rendering on the server (where it's safer, faster, and ships no JS), and move only the interactive bits to the client. "Server by default" is not a performance trick — it's the correct default for most content, which is not interactive. Client components are the exception, not the rule.

What each can and can't do

Server Component (default)Client Component ('use client')
Fetch dataawait directly inside the component; reads DB / secrets safelyMust fetch over HTTP (e.g. a Route Handler) from the browser
useState/useEffect/onClick❌ not allowed✅ this is the whole point
Browser APIs (window, localStorage)❌ no browser✅
Ships JS to the browserNo component JS — sends finished HTMLYes — its code is in the client bundle
async component✅ export default async function❌ (use hooks / use() instead)

The boundary rule that trips everyone up

'use client' is a boundary, not a per-component switch. Once a file is marked, all its imports and child components become client too. That's exactly why a top-of-tree 'use client' drags the whole page into the browser — the Session 4 anti-pattern.

The correct shape

A Server Component can import and render a Client Component (great — server page, client leaf). The reverse is restricted: a Client Component can't import a Server Component, but it can receive one as a children prop (the "donut"/slot pattern).

Draw the boundary as low in the tree as you can. Everything above the leaf stays on the server.

5Rendering, Suspense & streaming

A slow await shouldn't mean a blank screen. Next streams the page: shell first, slow regions fill in as their data resolves.

Philosophy — Perceived speed matters more than actual speed Users judge performance by time-to-first-meaningful-content, not total load time. A page that shows a header and sidebar in 100ms and fills in slow data at 2s feels faster than a page that shows nothing for 2s then appears fully formed. Suspense + streaming is Next.js encoding that psychology into the rendering model: send what you have now, stream the rest as it arrives.

Three levers, increasing granularity

  1. loading.tsx — name the file and Next auto-wraps the whole route in a <Suspense> boundary. Streams the page as one unit. Zero isLoading state.
  2. Explicit <Suspense fallback> — wrap individual async sections so a fast card isn't blocked by a slow one. Each boundary resolves independently.
  3. Promise.all — for independent fetches in the same component, start them together to avoid a request waterfall.
sequenceDiagram
  participant B as Browser
  participant N as Next.js (server)
  participant P as page.tsx
  participant L as loading.tsx
  B->>N: GET /dashboard
  N->>L: render loading.tsx instantly
  N-->>B: stream skeleton UI
  N->>P: await getSlowSummary() (2s)
  P-->>N: data ready
  N-->>B: stream real content, swap out skeleton

loading.tsx is Suspense with a default boundary. The trainee question "what is loading.tsx built on?" → React Suspense.

Waterfall vs parallel. const a = await x(); const b = await y(); runs sequentially (waterfall). const [a,b] = await Promise.all([x(),y()]) runs them together. 600ms + 1200ms becomes ~1.2s instead of ~1.8s.

6Reading data + Route Handlers

The default way to read data is no special way at all: make the component async and await your fetch/DB call inline. The browser receives finished HTML and ships zero fetching JavaScript.
Philosophy — Eliminate the round trip The traditional SPA pattern for initial data is: server sends empty HTML → browser fetches bundle → React renders skeleton → component effect fires → browser fetches data → component re-renders with data. That is four network hops before the user sees anything real. A Server Component collapses all of that into one: the server fetches data while building the HTML response, and the browser receives finished content in the same request that served the page. Fewer hops, less JS, no secrets leaking to the client. 
// Server Component — runs on the server, never in the browser
export default async function UsersPage() {
  const users = await getUsers();      // DB / fetch / file — safe here
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}

When you genuinely need a browser fetch → Route Handler

A Client Component can't import the server-only data functions. The bridge is a Route Handler — app/api/users/route.ts exporting GET/POST/… and returning a Response. That's the App Router's equivalent of an API route.

// src/app/api/users/route.ts
export async function GET() {
  const users = await getUsers();
  return Response.json(users);
}

7Server Actions & mutations (the write half)

A 'use server' function can be passed straight to <form action={fn}>. It runs on the server, receives the FormData, mutates, then calls revalidatePath('/route') to re-render the Server Component with fresh data. No onSubmit, no fetch, no manual re-fetch.
Philosophy — Reclaim the native form HTML forms have submitted data to servers since 1993 — without JavaScript, without state management, without a fetch call. Single-page apps abandoned this by wiring everything through JavaScript event handlers and client-side fetch. Server Actions restore the original model: a real <form> that posts directly to a server function. The server mutates, revalidates the affected route, and the framework handles the UI update. The whole write cycle collapses to one function and one call to revalidatePath — no Redux, no manual re-fetch, no optimistic update bookkeeping required for the common case.

The simplest write

// actions.ts
'use server';
import { revalidatePath } from 'next/cache';

export async function signGuestbook(formData: FormData) {
  const name = String(formData.get('name') ?? '');
  if (!name) return;                 // validation runs on the server
  await addGuestbookEntry(name);
  revalidatePath('/guestbook');      // re-render the list, no manual re-fetch
}
// page.tsx (Server Component)
<form action={signGuestbook}>
  <input name="name" />
  <button>Sign</button>
</form>

Progressive enhancement

Because this renders a real <form> posting to a server action, it works with JavaScript disabled. JS is an enhancement, not a requirement. Great demo: turn off JS in devtools and submit — it still works.

When you need pending / error UI → useActionState

The plain form gives no feedback. useActionState adds a pending flag and lets the action return error state. The action signature changes: it takes (previousState, formData) and returns the next state.

// add-todo-form.tsx
'use client';
import { useActionState } from 'react';

const [state, formAction, pending] = useActionState(addTodoAction, {});
// <form action={formAction}> … <button disabled={pending}>{pending ? 'Adding…' : 'Add'}</button>
// {state.error && <p className="err">{state.error}</p>}
// actions.ts
'use server';
export async function addTodoAction(prevState, formData) {
  const text = String(formData.get('text') ?? '');
  if (!text) return { error: 'Todo cannot be empty' };  // returned state
  await addTodo(text);
  revalidatePath('/todos');
  return {};
}

Say this out loud in S3

Server Actions are reachable by a direct POST, not just your form. A real app must check auth/authorization inside every action — the demo skips it, but never let trainees think the form is the security boundary.

About error.tsx — be precise

The boundary must be a Client Component and receives error. v16 (16.2) adds unstable_retry() — it re-fetches and re-renders the boundary's children, and is now the recommended recovery. The classic reset() still exists but only clears the render-error state without re-fetching — so it won't recover a Server Component / data error. The session script uses reset(), which is fine for the demo (the page throws during render); just know the distinction if asked.

9Caching & Cache Components — the day-2 concept

You teach this as an idea, not an API. Three minutes, no drilling.

Philosophy — Correctness before speed Caching is the single most powerful performance lever Next.js offers, and the single most common source of subtle bugs (stale data, build errors, cache misses). Teaching it on day one alongside routing and server components overloads trainees and trains them to reach for caching before they understand when they need it. The correct order: understand the rendering model → understand mutations → then add caching as a targeted optimization. Cache Components OFF is not a limitation of this course; it is the pedagogically correct baseline.
  • Next.js can cache parts of a page and even pre-render them at build time.
  • v16's model is Cache Components — the 'use cache' directive plus Partial Pre-Rendering (PPR). It's opt-in via cacheComponents: true in next.config.ts.
  • It's the single trickiest part of the framework — which is exactly why this repo keeps it OFF. With it off, a component reading runtime data simply renders per request, no build error.
  • revalidatePath / revalidateTag are the simple, model-agnostic refresh and work fine with Cache Components off — no 'use cache' needed.

Do NOT turn it on

The repo's AGENTS.md forbids adding cacheComponents to the config. Turning it on introduces "uncached data outside Suspense" build errors that derail every demo. Caching is a later course.

10When NOT to use Next.js

Knowing when to reach for something simpler is itself a best practice — present it as a decision, not a sales pitch.

Philosophy — Right tool, right job Next.js is a powerful framework. Power has cost: a Node.js runtime requirement, Turbopack as a build dependency, a React rendering model that distinguishes server from client. For a landing page or a purely internal admin tool that will never be crawled, that cost buys nothing. A good engineer reaches for the simplest tool that meets the requirements, not the most impressive one.

11Probable trainee Q&A

React vs Next.js & SSR

Why do I need Next.js if React already renders components?

React is a UI library — it renders components, nothing more. You still need something to handle routing, bundling, server-side rendering, and API endpoints. You can wire all that up yourself (Vite + react-router + an Express server + your own SSR setup), or you can use Next.js, which does it all with zero configuration. Next.js is the framework around React.

What exactly is "server-side rendering" — what does the server actually do?

The server runs your React components as Node.js functions. They can await databases and APIs, then return JSX. Next.js renders that JSX to HTML strings and sends them to the browser in the HTTP response — fully populated, no JavaScript needed to see the content. The browser then hydrates (attaches event listeners) to make interactive parts work.

What is hydration?

The browser receives pre-rendered HTML from the server — it looks right, but event handlers aren't attached yet. Hydration is the step where React on the browser side "takes over" the existing HTML: it attaches onClick, onChange, and other event handlers without repainting anything. The page was already visible; hydration just makes it interactive. Only Client Components hydrate — Server Components never run in the browser at all.

Is SSR the same as SSG (Static Site Generation)?

No. SSR renders on every request — fresh data every time. SSG renders at build time — the HTML is generated once and reused for every visitor until the next build. Next.js supports both; in the App Router with Cache Components OFF (our course default), pages are SSR by default. SSG is achieved by turning on caching — a day-2 topic.

Routing & the App Router

Why do I have to await params now? It used to be a plain object. v16

In v16 params and searchParams are Promises. Awaiting them lets Next start rendering the rest of the page before those values are resolved, which supports streaming and the new caching model. In v15 the sync form still worked with a warning; in v16 it's removed. Old tutorials doing params.slug directly will error.

What's the difference between a route group (x) and a normal folder?

A normal folder name becomes a URL segment. A folder wrapped in parentheses — (s1-routing) — is a route group: it organizes files and can scope a layout, but it disappears from the URL. So (s1-routing)/about/page.tsx is just /about.

Why <Link> instead of a plain <a>?

<Link> does client-side navigation — no full page reload — and prefetches the linked route automatically (in production; not in dev). The payload depends on loading.tsx: routes without one prefetch the whole page; routes with one prefetch from the layout up to the first loading boundary. A plain <a> is a full document navigation and loses all of that. Use prefetch={false} to opt out.

Do I have to import a layout into my page?

No — layouts apply by position in the tree. A layout.tsx automatically wraps every page.tsx in its folder and all child folders. The page never imports it. Nesting is automatic too: root layout → section layout → page.

When does not-found.tsx vs error.tsx show?

not-found.tsx renders when you call notFound() (a deliberate "this resource doesn't exist" signal — typically a 404). error.tsx renders when the segment throws an unexpected error — it's a React error boundary with a retry. Different intents: "expected absence" vs "something broke."

Why must error.tsx be a Client Component? gotcha

It's a React error boundary, and it needs an interactive retry callback (a function prop you wire to an onClick). Interactivity requires the browser, so it must be 'use client'. In v16 (16.2) the recommended recovery is unstable_retry() (re-fetches and re-renders the boundary's children); the older reset() only clears the render-error state without re-fetching.

Server vs Client Components

How do I decide: Server Component or Client Component? core

Ask one question: does this component need state, effects, event handlers, or browser APIs? If no → Server Component (the default) — fetch data inline, ship HTML. If yes → 'use client', but keep it as a small leaf. Default to server; opt into client only where you truly need it.

Why can't I use useState/useEffect in a Server Component?

Server Components render once on the server and never run in the browser, so there's no component lifecycle, no re-render, no DOM — the things hooks rely on. State and effects are inherently client concepts. The moment you need them, that file (a leaf) becomes 'use client'.

If I put 'use client' at the top of my page, what actually happens?

You move a boundary, not flip a switch. Everything that file imports — and all its children — becomes part of the client bundle and runs in the browser. So a top-of-tree 'use client' drags the whole page client-side: more JS, hydration, and (if you fetch in useEffect) a spinner. That's exactly the Session 4 anti-pattern.

Can a Server Component render a Client Component, and vice versa?

A Server Component can import and render a Client Component freely — that's the normal "server page, client leaf" shape. A Client Component can't import a Server Component, but it can receive one through children (or any prop) — the "slot"/donut pattern: <ClientWrapper><ServerThing/></ClientWrapper> composed in a server parent.

Can I pass a function as a prop from a Server to a Client Component?

Not an arbitrary function — props crossing the boundary must be serializable (they're sent as data). The exception is a Server Action (a 'use server' function), which is passable because Next turns it into a callable reference. Plain callbacks belong inside the client side.

Can I still use Redux / Context / React Query?

Yes, but inside the client boundary. Context providers and client state libraries live in 'use client' components (often a provider near the root of the client tree). For server data you usually don't need React Query at all — you await in a Server Component. Mix them: server for data, client libs for genuinely client-side state.

Data fetching & streaming

Where does the fetch in a Server Component actually run?

On the server, during render — never in the browser. View source and the data is already in the HTML; the Network tab shows no client-side /api call. That means DB queries, secrets, and credentials stay server-side and never reach the client.

Is it safe to query the database or use an API key directly in a component?

In a Server Component, yes — that code only runs on the server and is never sent to the browser. That's a core benefit. The danger is doing it in a 'use client' file, where the code ships to the browser. Keep secret-touching code server-side (Server Components, Route Handlers, Server Actions).

What is loading.tsx built on? Is it the same as Suspense?

It is Suspense. Naming a file loading.tsx tells Next to automatically wrap that route's page.tsx (and children) in a <Suspense> boundary, using your file as the fallback. For finer control you drop explicit <Suspense fallback> around individual sections instead.

loading.tsx vs an explicit <Suspense> — when do I use which?

loading.tsx streams the whole route as one unit — one fallback for the page. Use explicit <Suspense> when you want sections to appear independently: a fast card shows while a slow card still streams. Same primitive, different granularity.

Why did my two awaits make the page slow? (waterfall)

Sequential awaits run one after another — the second request waits for the first. If the two fetches don't depend on each other, start them together with const [a, b] = await Promise.all([x(), y()]). 600ms + 1200ms then takes ~1.2s instead of ~1.8s.

How does Next decide what to send first when streaming?

It sends the static shell (and any already-resolved content) immediately, then streams each Suspense boundary's content as that boundary's await resolves. The user sees structure right away; slow regions swap in their real content as they finish — no blank screen, no blocking on the slowest piece.

Is server-rendered HTML good for SEO?

Yes — that's a key reason to use Next. Crawlers get fully-rendered HTML with the content already present, plus per-page <title>/meta from generateMetadata. The useEffect-fetch anti-pattern ships an empty shell first, which is worse for SEO and perceived speed.

Server Actions & mutations

What's the difference between 'use client' and 'use server'? core

They're opposite directives. 'use client' marks a component boundary — "this and its imports run in the browser." 'use server' marks functions as Server Actions — "this is callable from the client but its body only ever executes on the server." One is about where components run; the other is about exposing a server function to the client.

After I POST a change, how does the list on screen update without me re-fetching?

revalidatePath('/route'). After the action mutates the data, that call tells Next to re-run the route's Server Component, which re-reads the store and streams fresh HTML back. One round trip does both the write and the UI refresh — no manual setState, no client re-fetch.

revalidatePath vs revalidateTag? v16

revalidatePath('/route') invalidates a specific path. revalidateTag('tag', profile) invalidates everything tagged with that tag across the app — note v16's new second argument (a profile, e.g. 'max'); the old single-arg form is deprecated. For this course we use revalidatePath, whose signature didn't change. Tags matter mainly once you're caching.

Does the whole page re-render on revalidatePath, or just the data?

Next re-renders the affected route's Server Components on the server and streams the updated HTML; on the client it reconciles, so layouts and client state that aren't part of the changed tree are preserved. You don't re-download the whole document — it's a targeted server re-render, not a full page reload.

Do Server Actions really work without JavaScript?

For the plain <form action={serverFn}> case, yes — it renders a real HTML form that posts to the action, so the browser's native submit carries it even with JS disabled. That's progressive enhancement. The moment you add useActionState for live pending/error UI, that feedback needs JS, but the underlying submit still degrades gracefully.

Are Server Actions secure? Can someone call them directly?

Treat them like any public POST endpoint — they can be invoked directly, not just from your form. Next adds protections (e.g. action IDs, same-origin checks), but you must do auth and authorization checks inside every action. The form is not a security boundary. The demo skips auth for brevity; a real action checks the session first.

What's the useActionState signature again?

Hook: const [state, formAction, isPending] = useActionState(action, initialState). The action it wraps takes (previousState, formData) and returns the next state. You wire action={formAction} on the form, read isPending for the button, and render errors from the returned state.

Why is the add-todo form a Client Component but the toggle forms aren't?

Only the add form needs the useActionState hook (pending flag + error message), and hooks require 'use client'. The toggle is a plain <form action={fn}> with no client feedback, so it stays a server-rendered form. Default to the plain form; reach for the client leaf only where you need live feedback.

Do I still need /api routes if I have Server Actions?

For form-driven mutations from your own UI, Server Actions usually replace hand-rolled POST endpoints. You still want Route Handlers (route.ts) for things that need a real HTTP endpoint: webhooks, third-party callbacks, public/mobile APIs, or fetching from a Client Component that isn't a form.

v16, tooling & "why is my old code wrong"

What is Turbopack and do I need the --turbopack flag? v16

Turbopack is Next's Rust-based bundler, now stable and the default for both dev and build in v16 — no flag needed. If you copied next dev --turbopack from an old guide, drop the flag. To fall back to Webpack you'd explicitly pass --webpack.

My tutorial uses middleware.ts — is that gone? v16

It was renamed to proxy.ts in v16 to make clear it runs at the network/edge boundary, not as in-app middleware. Same idea, new name. We don't use it in this course, but that's the answer if someone's old project breaks on upgrade.

Why is cookies() / headers() returning a Promise? v16

In v16 these dynamic APIs are async-only — await cookies(), await headers(), await draftMode(). The synchronous versions were removed (they warned in v15). Same reasoning as await params: it unlocks streaming and the new rendering model.

What React version is this, and do I install it separately?

v16's App Router ships on React 19.2 (a React canary built into the framework), so you get React 19 features like the new form/action hooks and View Transitions. You declare React in package.json for type compatibility, but the framework bundles what it needs.

Why is Cache Components off? Isn't caching the whole point of Next? course

Caching is powerful but it's the trickiest part of the framework, and turning it on forces you to reason about "uncached data outside Suspense" build errors on day one. Off (the v16 default) means async data fetching just works, so we can teach routing, server components, and actions cleanly. Caching is a deliberate day-2 topic.

This is a server component — how do I add a click handler / use window?

You can't, in that file. Extract the interactive bit into a small child component, put 'use client' at the top of that file, and render it from the server component. Keep the boundary as low as possible so only the interactive leaf ships JS.

Architecture & judgment (Session 4)

What's actually wrong with the anti-patterns page? It works fine.

It produces the right screen the wrong way: 'use client' at the top (nothing is interactive), useEffect + fetch to read data the server already had, and an extra hop to /api/users. Result: more JS, hydration, and a spinner on every load. The fix is one deletion ('use client') and one keyword (async) — it becomes the server version.

So is useEffect-to-fetch always wrong?

Not always — it's right for genuinely client-side, post-interaction data (e.g. data that depends on browser state or live user input). It's wrong as the default way to load a page's initial data, because a Server Component does that in one line with no spinner and less JS. The anti-pattern is using the client tool for a server job.

Where exactly should the client boundary go?

At the lowest component that truly needs interactivity — the button, the input, the form with feedback. Everything above it stays a Server Component. "Server by default, client at the leaves" is the single decision that separates good Next.js from bad.

When would you NOT use Next.js?

A brochure/content site with little interactivity (plain HTML or Astro is lighter); a purely internal SPA with no SEO and no server rendering (Vite + React is simpler); or anywhere you can't run a Node/serverless host. Next wins when you need server-rendered HTML and rich interactivity and server data in one app.

In-memory store — why does my data reset?

The demo's data.ts uses plain in-memory arrays, which reset when the dev server restarts (and aren't shared across server instances). That's fine for teaching. In a real app the action writes to a database at the same spot — the action/revalidatePath pattern is identical; only the storage changes.
